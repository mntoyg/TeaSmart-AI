หลังกำหนดสาธิตเลื่อนจาก 2026-10-22 ไปเป็น **2026-11-21**

เจ้าของทั้งไฟล์: **`ml/` และ `backend/` — Claude Code** ยกเว้นข้อ 6 ที่เป็นงานร่วม
กับ Codex และระบุไว้ชัดในข้อนั้น รายการ "อะไรยังพังอยู่" อยู่ใน
[PRODUCTION-READINESS.md](PRODUCTION-READINESS.md) ไฟล์นี้ตอบเฉพาะว่า

**กฎข้อเดียวของไฟล์นี้:** งานที่ไม่จบด้วยตัวเลขที่พูดบนเวทีได้ ไม่อยู่ในรายการนี้

## สิ่งที่ตัดสินใจแล้วว่า **ไม่ทำ** — อ่านก่อน เพราะมันประหยัดเวลาที่สุด

**ไม่เทรนใหม่เพื่อไล่ accuracy** ตอนนี้อยู่ที่ **0.9871 · macro-F1 0.9873**
บนชุดทดสอบ 1,245 ภาพ การดันเลขนี้ขึ้นอีก 0.005 ไม่เปลี่ยนอะไรสำหรับเกษตรกร
สักคน และไม่เปลี่ยนใจกรรมการสักคน **ช่องว่างจริงอยู่ที่อื่นทั้งหมด**

ตามมาด้วยสิ่งที่ไม่ทำเพราะไล่แกนเดียวกัน: test-time augmentation,
backbone ใหญ่ขึ้น, ensemble, fp16 (int8 ถูกปฏิเสธไปแล้ว เหตุผลใน
[EVIDENCE.md](EVIDENCE.md))

**ไม่เพิ่มคลาสที่หกชื่อ `not_a_leaf`** ไม่มีชุดข้อมูลสำหรับมัน และคลาสปิดที่หก
ก็ยังเป็นคลาสปิด มันย้ายปัญหา ไม่ได้แก้ปัญหา — ดูข้อ 1

**ไม่ใช้ LLM เขียนคำแนะนำ** `backend/app/kb/diseases.json` เป็นข้อความที่คนอ่าน
แล้ว ส่วน LLM จะแต่งชื่อสารเคมีและอัตราผสมที่ฟังดูถูกได้ทุกครั้ง
**ความเสียหายตกกับคนที่ฉีดพ่นตามที่เราบอก**

## ลำดับงาน

### 1. open-set rejection — ปิดช่องที่ใหญ่ที่สุด · สัปดาห์ 1–2

**ปัญหาที่วัดมาแล้ว** ภาพมือกำยอดชาสดสมบูรณ์ได้ `brown_blight` ที่ **92.4%**
ภาพถ่ายหน้าจอโน้ตบุ๊กได้ `brown_blight` ที่ **76.8%** ตัวจำแนกมีห้าคลาสปิด
**ทุกภาพถูกบังคับให้เป็นหนึ่งในห้าคลาสเสมอ** ไม่มีทางปฏิเสธ

`min_confidence = 0.60` ที่มีอยู่ไม่ช่วย ทั้งสองค่าข้างบนสูงกว่ามัน

**วิธี** คะแนนระยะห่างบน feature 1280 มิติชั้นก่อนสุดท้ายของ MobileNetV3-Large
ไม่ใช่บน softmax: fit ค่ากลางและความแปรปรวนร่วมของแต่ละคลาสบนชุด `train`
แล้วคิดระยะ Mahalanobis ของภาพใหม่ไปยังคลาสที่ใกล้ที่สุด เทียบกับ baseline
สองตัวคือ maximum softmax probability และ energy score เลือกตัวที่วัดได้ดีที่สุด
ไม่ใช่ตัวที่ฟังดูดีที่สุด

**ต้องมีชุดลบก่อนจึงจะวัดได้** ราว 300 ภาพที่ไม่ใช่ใบชา ถ่ายด้วยมือถือ:
มือ หน้าคน หน้าจอ พื้นปูน ดิน ท้องฟ้า ถนน ใบพืชชนิดอื่น ผ้า อาหาร
**ใบพืชชนิดอื่นและดินเป็นสองกลุ่มที่ยากที่สุด และเป็นสองกลุ่มที่เกษตรกรถ่ายจริง**

**เกณฑ์รับงาน** เลือก threshold บนชุด `val` ให้ **ใบชาจริงผ่าน ≥ 99%**
แล้วรายงานว่าปฏิเสธภาพที่ไม่ใช่ใบชาได้กี่เปอร์เซ็นต์ที่เกณฑ์นั้น
ลำดับนี้สำคัญ: ตัวตรวจที่ปฏิเสธใบที่เป็นโรคหนักทิ้งไป แย่กว่าไม่มีตัวตรวจ

**ส่งมอบ** `python -m teasmart_ml.cli reject` · ฟิลด์ใหม่ใน
[DESIGN.md](DESIGN.md) หัวข้อ 8 · ตัวเลขหนึ่งบรรทัดใน EVIDENCE.md
**และข้อจำกัดข้อที่สองใน README หายไปได้**

### 2. calibrate ความมั่นใจ · สัปดาห์ 1 ครึ่งวัน

**ปัญหา** ตัวเลข 92.4% ที่ขึ้นบนหน้าจอไม่ได้แปลว่าความน่าจะเป็น 92.4%
โมเดลที่เทรนด้วย cross-entropy มั่นใจเกินจริงเกือบทุกตัว

**วิธี** temperature scaling — สเกลาร์ตัวเดียว fit บนชุด `val`
**ไม่เปลี่ยน argmax ของภาพใดเลย** เปลี่ยนแค่เลขที่ผู้ใช้เห็น

**ส่งมอบ** ECE ก่อนและหลัง + reliability curve ใน EVIDENCE.md ·
ค่า temperature เสิร์ฟผ่าน `GET /api/v1/config` เพื่อให้เบราว์เซอร์
คิดเลขเดียวกับเซิร์ฟเวอร์

ถูกที่สุดในรายการนี้ และเป็นตัวเลขที่ทีมแฮกกาธอนแทบไม่มีใครรายงาน

### 3. แบ่งชุดข้อมูลใหม่แบบจัดกลุ่ม · สัปดาห์ 2

**ปัญหา** `datasets/manifest.py` สุ่มแบ่งภายในแต่ละคลาส ไม่ได้จัดกลุ่มตามครั้ง
ที่ถ่าย ภาพใบเดียวกันหลายช็อตจึงอยู่ได้ทั้งฝั่ง train และ test
**0.9871 จึงเป็นขอบบน ไม่ใช่ค่าประมาณในสนาม**

**วิธี** manifest มีคอลัมน์ `phash` อยู่แล้ว จับกลุ่มด้วยระยะ Hamming
แล้วส่งทั้งกลุ่มไปอยู่ split เดียว ไม่ใช่ทีละภาพ

**เตือนล่วงหน้า: ตัวเลขจะลดลง** และนั่นคือสิ่งที่ส่งมอบ
**"accuracy ลดจาก 0.9871 เหลือ 0.9x เมื่อเราจัดกลุ่มตามครั้งที่ถ่าย"
เป็นคำพูดที่หนักแน่นกว่า 0.9871 เปล่า ๆ** กับกรรมการที่รู้เรื่อง ML

**ผลข้างเคียงที่ต้องวางแผน** ทุกตัวเลขที่ตีพิมพ์แล้วใช้ไม่ได้ทันที
ต้อง regenerate EVIDENCE.md, README, DEMO.md (ผ่าน `scripts/prepare_demo.py`)
ในสัปดาห์เดียวกัน **ห้ามค้างสองชุดเลขไว้ในที่เก็บพร้อมกัน**

### 4. ภาพใบไหม้ที่มีป้ายกำกับ → ตัวเลข sensitivity · ภาคสนาม สัปดาห์ 2–3

**ปัญหา** ด่าน 4 ตัดสินโรค vs แผลไหม้ ซึ่งเป็นจุดแข็งที่สุดของงานนี้
และ **ไม่มีค่า sensitivity ของมันอยู่เลย** เพราะไม่มีภาพใบไหม้ที่มีป้ายกำกับ
ในแหล่งข้อมูลทั้งเก้าที่สำรวจ ที่มีคือ specificity **97.18%** บนภาพโรค 1,030 ภาพ
— บอกได้แค่ว่ามันไม่เรียกโรคว่าไหม้ **ไม่ได้บอกว่ามันหาไหม้เจอ**

**30 วันทำให้ข้อนี้เป็นไปได้ และเดิมมันเป็นไปไม่ได้** ต้องการราว 150–200 ภาพ:
ใบที่ไหม้จากแดดจัด จากปุ๋ยเข้ม จากลมหนาว ถ่ายคู่กับใบปกติในสภาพแสงเดียวกัน
**ติดป้ายโดยคนสองคนแยกกัน** และบันทึกว่าตรงกันกี่ภาพ

**ส่งมอบ** sensitivity ที่อ้างได้จริง **หนึ่งตัวเลข ที่วันนี้เราปฏิเสธที่จะพูด**
นี่คืองานที่คุ้มที่สุดต่อหนึ่งวันแรงงานในไฟล์นี้ และไม่ใช่งานโค้ด

### 5. ภาพจากไร่ชาจริงในประเทศไทย · ภาคสนาม สัปดาห์ 2–3

**ไม่มีภาพใดในคลัง 8,316 ภาพมาจากประเทศไทย** สินค้านี้ถูกสร้างเพื่อสิงห์ปาร์ค
และยังไม่เคยเห็นใบชาจากที่นั่นแม้ใบเดียว

**แค่ 50 ภาพพร้อมป้ายกำกับ รายงานแยกเป็นชุดของตัวเอง ก็เหนือกว่าคำอ้าง
ของทุกทีมในห้อง** ไม่ต้องเอาไปเทรน ใช้เป็นชุดทดสอบที่สองก็พอ และมีค่ากว่า

ทำข้อ 4 กับข้อ 5 ในทริปเดียวกัน

### 6. ย้ายด่าน 2, 4, 5 ลงเบราว์เซอร์ → `full` บนเว็บ · สัปดาห์ 3–4

**ปัญหา** เว็บทำได้แค่ `classifier_only` **คำตัดสินโรค vs ไหม้ และระดับ
ความรุนแรง ซึ่งเป็นสองอย่างที่แยกเราออกจากทีมอื่น ไม่ทำงานบนลิงก์ที่เราแจก**
ต้องมีโน้ตบุ๊กบนเวทีเพื่อสาธิต

**ทำได้จริงเพราะด่านพวกนี้ไม่ใช่โมเดล** ด่าน 2 คือ CV แบบกฎเกณฑ์ 120 บรรทัด
(excess green + แถบ HSV + contour ที่ใหญ่ที่สุด + convex hull) ด่าน 5 คือ
39 บรรทัด ด่าน 4 คือ 309 บรรทัด และเป็นงานหนักจริงของข้อนี้

**การแบ่งงาน** Claude Code เขียน implementation อ้างอิงและ parity fixtures
ใน `ml/` ให้ก่อน แล้ว **Codex เขียน TypeScript** โดยวัดเทียบ fixtures
รูปแบบเดียวกับที่ตัวจำแนกใช้อยู่แล้ว (ตรงกัน 50/50 ความน่าจะเป็นต่างสูงสุด
0.00283) **อย่าเริ่มฝั่ง TS ก่อน fixtures เสร็จ** ไม่งั้นได้ด่านที่สองฝั่งไม่ตรงกัน
ซึ่งเป็นบั๊กเดียวกับข้อ 8 ในใบสั่งงาน 2026-10-21

**ส่งมอบ** `analysis_mode: full` บนลิงก์สาธารณะ ไม่มีเซิร์ฟเวอร์
ภาพยังไม่ออกจากเครื่องผู้ใช้ **และตารางสองช่อง "ไม่ได้" ใน README หายไป**

### 7. Grad-CAM ชี้ว่าโมเดลดูที่ไหน · สัปดาห์ 4 ถ้าเวลาเหลือ

วาดความร้อนทับบนใบ ให้เห็นว่าโมเดลตัดสินจากรอยไหน **ไม่เพิ่มความแม่น
แม้แต่นิดเดียว** แต่เปลี่ยน "เชื่อเราสิ 92%" เป็น "ดูสิ มันมองที่รอยนี้"

ทำเป็นข้อสุดท้ายเพราะมันเป็นของประดับ ไม่ใช่ของจำเป็น — และถ้าข้อ 1 ยังไม่เสร็จ
มันจะชี้ให้เห็นชัด ๆ ว่าโมเดลมองมือคนแล้วตอบ `brown_blight`

## สิ่งที่ต้องทำก่อนทุกข้อ และใช้เวลาไม่ถึงวัน

**ด่านตรวจว่าในภาพมีใบชาหรือไม่ บนเบราว์เซอร์** ผู้ใช้สั่งมาเองว่า UI ต้อง
ตอบว่าไม่ใช่ใบไม้และไม่วิเคราะห์ต่อ ของนี้เป็นงานของ Codex ในใบสั่งงาน
[HANDOFF-CODEX.md](HANDOFF-CODEX.md) ข้อ H **แต่ค่า threshold เป็นงานของ `ml/`
และห้าม Codex เดาค่าเอง**

เหตุผลที่ห้ามเดา: ใบที่เป็นโรคหนักเป็นสีน้ำตาลเกือบทั้งใบ **มันมีสัดส่วน
พิกเซลเขียวต่ำกว่าภาพมือคนถือใบ** threshold ที่ตั้งจากสายตาจะปฏิเสธ
เคสที่สำคัญที่สุดของสินค้านี้ทิ้ง ต้องวัดการกระจายบนคลัง 8,316 ภาพก่อน
แล้วตั้งค่าไว้ใต้ค่าต่ำสุดที่ใบจริงเคยทำได้

ด่านนี้เป็นของชั่วคราวที่รู้ตัวว่าชั่วคราว **ข้อ 1 คือของจริง** และเมื่อข้อ 1 เสร็จ
ด่านนี้ถูกแทนที่
