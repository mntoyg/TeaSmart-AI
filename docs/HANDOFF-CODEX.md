### A. เปิดกล้องแล้วปิดไม่ได้ — ผู้ใช้รายงาน ตรวจยืนยันแล้ว

`frontend/src/pages/ScanPage.tsx` บรรทัด 123-124 เป็น ternary

```jsx
{camera ? <button onClick={takePhoto} disabled={busy}>ถ่ายภาพ</button>
  : <button className="secondary" onClick={openCamera} ...>เปิดกล้อง</button>}
```

**ตอนกล้องเปิด ปุ่มเดียวที่เรนเดอร์คือ `ถ่ายภาพ` ไม่มีปุ่มปิดอยู่เลยทั้งหน้าจอ**

`stopCamera()` (บรรทัด 22) เขียนไว้ถูกต้องและหยุด track ครบ **แต่ไม่มีทางเรียก
จาก UI ได้** ผู้ใช้ที่กดเปิดกล้องแล้วเปลี่ยนใจ มีทางออกแค่สองทาง: ถ่ายรูป
หรือเลือกไฟล์จากเครื่อง

**ทำไมมันหนักกว่าความรำคาญ** สตรีมกล้องยังเปิดอยู่ ไฟแสดงสถานะกล้องยังติด
และบน iOS จุดเขียวบน Dynamic Island ยังค้าง **กรรมการจะรู้สึกว่าแอปไม่ยอม
ปล่อยกล้อง** ซึ่งเป็นความรู้สึกเรื่องความเป็นส่วนตัว ไม่ใช่แค่ UX
และมันกินแบตด้วย

**แก้:** เพิ่มปุ่ม `ปิดกล้อง` ตอน `camera === true` ที่เรียก
`stopCamera(); setCamera(false);` **ให้ `ถ่ายภาพ` ยังเป็นปุ่มหลักอยู่**
คอมเมนต์เหนือบล็อก `.actions` อธิบายไว้แล้วว่าทำไมการถ่ายต้องเป็น primary
ตอนกล้องเปิด — อย่าไปสลับลำดับนั้น

**test ที่ต้องแดงก่อน:** เปิดกล้อง กดปิด แล้ว assert ว่า track ทุกเส้นถูก
`stop()` และ UI กลับไปแสดงปุ่ม `เปิดกล้อง` ใช้ mock ของ `getUserMedia`
ที่สอดแนมการเรียก `stop()` ได้

### B. กล้องค้างเปิดถ้าภาพที่ถ่ายใหญ่เกินเพดาน — เจอระหว่างตรวจข้อ A

**test:** ป้อนไฟล์ที่เกินเพดานเข้า `choose()` ขณะกล้องเปิด แล้ว assert ว่า


`backend/app/services/quality.py` ปฏิเสธเมื่อ `exposure_mean > exposure_max_mean`
**เท่านั้น** และมีคอมเมนต์ยาวอธิบายว่า clipping ฝั่งสว่าง **ถูกวัดและรายงาน
แต่จงใจไม่ให้เป็นเหตุผลในการปฏิเสธ ตั้งแต่ 2026-10-19** เพราะตอนที่มันเคย
ปฏิเสธได้ **มันปฏิเสธใบชาที่ถ่ายบนกระดาษขาวทุกใบ — สามจากสามภาพ agml
ทดสอบสดกับ endpoint จริง** เหตุผลคือพิกเซลที่สว่างจัดคือพื้นหลัง ไม่ใช่ใบ
และพื้นหลังที่สว่างไม่ได้บอกว่าใบเสียรายละเอียด

**เบราว์เซอร์ยังเป็นเวอร์ชันก่อนการแก้นั้น** และบน deploy แบบ static
**ด่านของเบราว์เซอร์คือด่านเดียวที่ทำงาน** กรรมการที่ถ่ายใบบนกระดาษขาว
บนโต๊ะสีอ่อน หรือกลางแดด จะได้ `ภาพสว่างเกินไป กรุณาหลีกเลี่ยงแสงแดดจัดส่องตรง`
**แล้วสแกนไม่ได้เลย** ไม่ใช่ผลที่แย่ แต่คือไม่มีผล

**แก้:** ตัด `|| clippedHigh > settings.clip_max_pct` ออกจากเงื่อนไขปฏิเสธ
**แต่ยังคงรายงาน `clipped_high_pct` ต่อไป** ให้เหมือน backend ทุกประการ
ส่วน clipping ฝั่งมืดยังเป็นเหตุผลปฏิเสธเหมือนเดิมทั้งสองฝั่ง อย่าแตะ
**test:** เฟรมที่มีพิกเซล 255 เกิน `clip_max_pct` แต่ค่าเฉลี่ยอยู่ในช่วง
**ต้องผ่าน** และต้องแดงก่อนแก้

### 10. `storage.ts` จะทำฐานข้อมูลของผู้ใช้เดิมพังทุกคน ตอนขึ้น schema เวอร์ชันหน้า

```js
if (!db.objectStoreNames.contains('scans')) db.createObjectStore('scans', ...);
if (!db.objectStoreNames.contains('metadata')) db.createObjectStore('metadata');
db.createObjectStore('config');                    // <- ไม่มีการ์ด
db.createObjectStore('queue', { keyPath: 'scan_id' });  // <- ไม่มีการ์ด
```

สองตัวแรกมีการ์ด สองตัวหลังไม่มี วันนี้ยังไม่พังเพราะ `upgrade` ไม่ถูกเรียก
สำหรับคนที่อยู่เวอร์ชัน 2 แล้ว **แต่วันที่ bump เป็นเวอร์ชัน 3**
`upgrade` จะรันกับผู้ใช้เวอร์ชัน 2 ทุกคน แล้ว `createObjectStore('config')`
จะโยน `ConstraintError` → `openDB` reject → **ทุกการเรียก store พังหมด
ประวัติและคิวเข้าไม่ถึง**

**แก้:** ใส่การ์ด `contains()` ให้ครบทั้งสี่ตัว
**test:** เปิดที่เวอร์ชัน 2 แล้ว bump เป็น 3 ต้องไม่โยน

### 11. `applyBatch` ปล่อยให้ความล้มเหลวที่ไม่ใช่ 4xx ค้างในคิวตลอดกาล

`storage.ts` — มีแค่ `[400, 413, 415, 422]` ที่ทำให้ entry กลายเป็น `failed`
ถ้าเซิร์ฟเวอร์ตอบ 500 หรือ 503 entry จะคง `pending` **และถูกส่งซ้ำทุกครั้งที่
`revision` ขยับ ไม่มี backoff ไม่มีตัวนับครั้ง ไม่มีเพดาน**
ตั้งใจให้ retry ข้อผิดพลาดชั่วคราวซึ่งถูก แต่ไม่มีทางออกถ้ามันไม่ชั่วคราว

**แก้:** นับจำนวนครั้ง เกิน N แล้วทำเป็น `failed` พร้อมข้อความไทย

### 12. `enqueue` และ `applyBatch` เก็บ object ดิบ ส่วน `save` เก็บค่าที่ผ่าน `parseStored`

```js
save:       put('scans', parseStored(result))   // เก็บค่าที่ return
enqueue:    parseStored(result); put('scans', result)   // ทิ้งค่าที่ return
applyBatch: results.forEach(parseStored); put('scans', result)  // ทิ้งเช่นกัน
```

ถ้า `parseStored` ทำแค่ตรวจ ก็ไม่ต่างกัน **แต่ถ้ามันปรับรูปอะไรสักอย่าง
สองเส้นทางนี้จะเก็บคนละรูป** ให้ทำให้เหมือนกันทั้งสามที่ ไม่ว่าคำตอบจะเป็นทางไหน

### 13. `resize.ts` ส่ง helper ที่ใช้เฉพาะตอนทดสอบขึ้นเว็บไปด้วย

`pixelByte` และ `sourceImage` มีคอมเมนต์เขียนไว้เองว่า *"Test-only; the app
never calls this"* แต่ถูก `export` จากโมดูลที่ `inference.ts` import
**ตรวจว่า rollup tree-shake มันออกจริงหรือไม่ อย่าเดา** ถ้าไม่ออก ให้ย้ายไป
ไฟล์แยกใต้ `src/test/` ความสำคัญต่ำสุดในรายการนี้

**P2-2 · `parseKnowledge` บังคับให้มี record เท่ากับ 6 รายการพอดี**
โรคที่เจ็ดจะทำให้ client พัง `scripts/snapshot_api.py` มี test ที่เฝ้าเรื่องนี้ฝั่ง backend แล้ว
แต่ฝั่ง client ยังพัง

**P2-3 · `TEASMART_CORS_ORIGINS`**
ต้องตั้งถ้า PWA ที่ build ถูกเสิร์ฟจาก origin อื่นที่ไม่ใช่ `localhost:5173`
**แผนที่เลือกไว้คือ static-only จึงไม่มี backend และข้อนี้ไม่มีผล** แต่ถ้าเปลี่ยนใจ
ไป deploy backend ด้วย ข้อนี้กลับมาทันที dev proxy ปิดปัญหานี้ไว้ จะไม่เห็นในเครื่อง

### P3 — ไม่ต้องทำก่อนสาธิต

- fp16 ONNX จะลดโมเดลจาก 16.8 MB เหลือราว 8.4 MB **ยังไม่ทดสอบ**

- 32 ภาพถูกสองแหล่งติดป้ายไม่เหมือนกัน ถูกตัดทิ้งแทนที่จะเดา

## 4. ตัวเลขที่พูดผิดแล้วเสียหาย

- **ไม่มีค่า sensitivity ของการตรวจใบไหม้ และห้ามอ้าง รวมถึงบนเวที**
  มีแต่ specificity ที่วัดได้ **97.18%** — `docs/EVIDENCE.md` หัวข้อ 5.5
- **specificity สูงอาจหมายความว่าตัววิเคราะห์ไม่ได้มอง** การรันครั้งแรกได้ 99.22%
  ขณะที่หาแผลไม่เจอบนใบที่เป็นโรค **59%** ดูจำนวน no-measurable-lesion ก่อนเชื่ออัตราใด ๆ
- **accuracy 0.987 เป็นขอบบน ไม่ใช่ค่าประมาณความแม่นในสนาม** การแบ่งชุดไม่ได้จัดกลุ่ม
  ตามครั้งที่ถ่าย
- **ตัวจำแนกผิดได้แบบมั่นใจ** มีภาพทดสอบหนึ่งภาพผิดที่ความเชื่อมั่น **0.983**
  ไม่มีหน้าจอไหนนำเสนอผลว่าแน่นอนได้
- **ไม่มีภาพใดในคลังมาจากสิงห์ปาร์ค**
- **threshold ของด่าน 1 และ `min_confidence` วัดมาแล้ว — วัดใหม่ ห้ามขยับมือ**

## 5. ตรวจงานอย่างไร

```bash
./scripts/test.sh
```

ต้องจบด้วย `All green.` ขณะส่งงานนี้คือ **163 backend, 120 ml, 73 frontend** และ ruff สะอาด
`test.sh` รันสิ่งเดียวกับที่ CI รันในลำดับเดียวกัน

**รันทั้งชุดก่อน push ทุกครั้ง** CI จับของที่พังมาแล้วครั้งหนึ่ง จากการรันแค่ชุดเดียว
หลังแก้ fixture ที่สองชุดอ่านร่วมกัน

สองชุดใช้ virtualenv แยกกันและ**ไม่เคย activate**:

```bash
cd backend && ./.venv/Scripts/python.exe -m pytest -q
cd ml && ./.venv/Scripts/python.exe -m pytest -q
```

**ห้าม `grep -rn` จาก root ของ repository** มันเดินเข้า `.venv` ทั้งสองต้นและ `data/`
แล้วชน timeout ให้จำกัดขอบเขต เช่น `grep -rn pattern frontend/src`

**`npm run build` ไม่พอที่จะบอกว่า static deploy ใช้ได้** ต้องเสิร์ฟ `dist`
โดยไม่มี backend แล้วดู network จริง วันนี้วิธีนี้คือสิ่งที่เจอว่า `/api/v1/config`
กับ `/api/v1/kb` ตอบ 404 ทั้งที่หน้าเว็บเรนเดอร์ปกติ
