**ไฟล์นี้ไม่ใช่รายการสำหรับวันสาธิต** ของสำหรับวันสาธิตอยู่ใน

## ระดับ 1 — ต้องแก้ก่อนให้เกษตรกรจริงใช้ ไม่ใช่ก่อนขึ้นเวที

### 1. โมเดลเรียกใบที่แข็งแรงว่าเป็นโรค ที่ความมั่นใจ 92.4%

วัดเมื่อ 2026-10-21 บน iPhone XS ภาพมือกำยอดชาสดสมบูรณ์ ได้ `brown_blight`
ที่ **92.4%** และภาพหน้าจอโน้ตบุ๊กได้ `brown_blight` ที่ **76.8%**

**นี่ไม่ใช่บั๊ก มันคือข้อจำกัดเชิงโครงสร้าง** ตัวจำแนกมีห้าคลาสปิด ไม่มี
open-set rejection ด่านคุณภาพวัดความเบลอกับแสง ไม่ได้วัดว่าในภาพเป็นใบไม้
และเบราว์เซอร์ไม่มีด่านแยกใบ **ทุกภาพจึงถูกบังคับให้เป็นหนึ่งในห้าคลาสเสมอ**

ผลกับผู้ใช้จริงหนักกว่าผลบนเวทีมาก เกษตรกรที่ได้คำตอบนี้จะ**ฉีดพ่นสารป้องกัน
กำจัดโรคลงบนต้นที่ไม่ได้เป็นอะไร** เสียเงิน เสียเวลา และเพิ่มสารเคมีลงในแปลง
โดยไม่จำเป็น **ความเสียหายตกกับคนที่เชื่อเรา**

งานที่ต้องทำ เรียงตามที่ควรทำก่อน:
- ตัวตรวจว่าในภาพเป็นใบชาหรือไม่ ก่อนเข้าตัวจำแนก (คลาส `not_a_leaf`
  หรือ out-of-distribution detector)
- calibrate ความมั่นใจ (temperature scaling บนชุด validation) ตอนนี้
  ตัวเลข 92.4% ไม่ได้แปลว่าความน่าจะเป็น 92.4%
- ขยาย `min_confidence` ให้ต่างกันตามคลาส ไม่ใช่ค่าเดียวทั้งห้าคลาส

**เจ้าของ: ml/ — Claude Code** ไม่ใช่งานของ Codex และไม่ใช่งานปรับ threshold

**2026-10-22** กำหนดสาธิตเลื่อนไป 2026-11-21 ข้อนี้จึงทำได้ทันแล้ว
แผนพร้อมวิธีและเกณฑ์รับงานอยู่ใน [AI-ROADMAP.md](AI-ROADMAP.md) ข้อ 1 และ 2

### 2. ไม่มีภาพจากไร่จริงในประเทศไทยแม้แต่ภาพเดียว

คลัง 8,316 ภาพมาจาก Kaggle, Mendeley และ AGML ทั้งหมด **ไม่มีภาพใดมาจาก
สิงห์ปาร์คหรือไร่ชาไทยใด ๆ** accuracy 0.9871 เป็นค่าบนชุดทดสอบที่มาจาก
การกระจายเดียวกับชุดเทรน **ไม่ใช่ค่าประมาณในสนาม และเราไม่รู้ว่าค่าจริงเท่าไร**

ข้อ 1 ข้างบนคือหลักฐานชิ้นแรกว่าช่องว่างนี้ใหญ่ ภาพจริงภาพแรกที่แอปเจอ
มันตอบผิดด้วยความมั่นใจสูง

**ต้องเก็บภาพจากไร่จริงพร้อมป้ายกำกับจากนักวิชาการเกษตร ก่อนอ้างตัวเลขใด ๆ
กับเกษตรกร** นี่เป็นงานภาคสนาม ไม่ใช่งานโค้ด

### 3. คำแนะนำการใช้สารเคมียังไม่มีใครรับรอง

`backend/app/kb/diseases.json` แนะนำสารป้องกันกำจัดโรคพืชอย่างเจาะจง
เอกสารบันทึกว่า record 0-3 เป็นข้อความที่ได้รับมา **แต่ไม่มีบันทึกว่าใครรับรอง
และรับรองเมื่อไร**

ก่อนเปิดให้คนทั่วไปใช้ ต้องมี: ชื่อผู้รับรองและวันที่ในไฟล์ · เวอร์ชันของ
ฐานความรู้ที่บันทึกคู่กับผลตรวจทุกครั้ง (เพื่อให้รู้ย้อนหลังว่าผู้ใช้คนหนึ่ง
ได้รับคำแนะนำฉบับไหน) · ข้อความปฏิเสธความรับผิดที่ผู้ใช้เห็นก่อนใช้ครั้งแรก

## ระดับ 2 — ต้องมีก่อนรับผู้ใช้จำนวนมาก

### 4. ยังไม่มี backend บนเน็ตเลย

ที่ deploy อยู่เป็น frontend อย่างเดียว **ทุกการสแกนเป็น `classifier_only`**
ไม่มีคำตัดสินโรค-กับ-ใบไหม้ และไม่มีความรุนแรง ซึ่งเป็นสองอย่างที่สินค้านี้
มีอยู่เพื่อมัน ผู้ใช้จริงจึงยังได้แค่ครึ่งเดียวของสินค้า

ต้องมี: host สำหรับ backend · TLS · `TEASMART_CORS_ORIGINS` ตั้งให้ถูก
(ตอนนี้ default เป็น `http://localhost:5173`) · และการตัดสินใจเรื่องความเป็น
ส่วนตัว เพราะ **การ deploy backend แปลว่าภาพของผู้ใช้จะออกจากเครื่องตัวเอง**
ซึ่งตอนนี้ไม่ออก

### 5. ไม่มีการจำกัดอัตราการเรียก

`POST /api/v1/scan` รัน pipeline ภาพเต็มทุกครั้ง **เปิดสู่อินเทอร์เน็ต
โดยไม่มี rate limit คือเปิดช่องให้ถล่ม CPU** `AGENTS.md` ข้อ 7 สั่งให้คิดแบบ
OWASP กับทุก input จากภายนอก แต่ยังไม่มีการจำกัดอัตรา

ต้องมี rate limit ต่อ IP และต่อ `scan_id` พร้อมเพดานขนาดคิวงาน

### 6. แคช idempotency อยู่ในหน่วยความจำ 512 รายการ และหายเมื่อรีสตาร์ต

`DESIGN.md` หัวข้อ 8.3 เขียนไว้เองว่าจงใจสำหรับเฟส 1 **แต่ไม่รอดเฟสถัดไป**
ผู้ใช้จำนวนมากจะหมุน 512 รายการทิ้งภายในไม่กี่นาที และ deploy แต่ละครั้ง
ล้างแคชทิ้งหมด ผลคือผู้ใช้ที่ส่งซ้ำได้ผลวินิจฉัยซ้ำซ้อน

ต้องย้ายไปที่เก็บข้อมูลจริง และนั่นหมายถึงข้อ 7

### 7. ไม่มีฐานข้อมูล

ไม่มีบัญชีผู้ใช้ ไม่มีประวัติข้ามเครื่อง ไม่มีบันทึกว่าใครได้รับคำแนะนำอะไร
เมื่อไร ข้อ 3 ต้องการบันทึกนั้น และข้อ 6 ต้องการที่เก็บ

### 8. ไม่เคยทดสอบโหลด ไม่รู้ว่ารับได้กี่คนพร้อมกัน

ONNX รันอยู่ในเส้นทางของ request ไม่มี worker pool ไม่มีคิว ไม่มีแผน
autoscale **ไม่มีใครรู้ว่าสิบคนพร้อมกันแล้วเกิดอะไรขึ้น** ต้องวัดก่อนเปิด

### 9. ไม่มี monitoring, log รวม หรือการแจ้งเตือน

ถ้าแอปพังสำหรับผู้ใช้จริง เราจะรู้ก็ต่อเมื่อมีคนบอก

### 10. การอัปเดตไปไม่ถึงเครื่องที่ติดตั้งไปแล้ว

`dist/sw.js` ไม่มี `skipWaiting` และ `main.tsx` ทิ้งค่า return ของ
`registerSW` service worker ตัวใหม่จึงค้างที่ `waiting` ตลอดไป
วันนี้แก้ด้วยการบอกผู้ใช้ให้ลบแล้วติดตั้งใหม่ **ซึ่งใช้กับผู้ใช้จริงไม่ได้**

**แปลว่าถ้าปล่อยไปแล้วพบบั๊ก เราแก้ไม่ถึงเครื่องใคร** ต้องทำ
`self.skipWaiting()` ใน `sw.ts` คู่กับ `registerType: 'autoUpdate'`
**เจ้าของ: frontend — Codex** และเป็นข้อที่สำคัญที่สุดในระดับนี้

## ระดับ 3 — ใช้ได้ทุกคน ไม่ใช่แค่คนที่เหมือนเรา

### 11. ยังไม่มีใครตรวจเรื่องการเข้าถึง

ไม่มีหลักฐานว่าเคยทดสอบกับ screen reader เคยวัดค่าคอนทราสต์ เคยลองขนาด
ตัวอักษรใหญ่ของระบบ หรือเคยวัดขนาดพื้นที่กดตามเกณฑ์ **ผู้ใช้เป้าหมายคือ
เกษตรกร ซึ่งรวมผู้สูงอายุที่สายตาไม่ดี** และบางส่วนใช้มือถือรุ่นเก่าจอเล็ก

ต้องทำ: วัดคอนทราสต์ตาม WCAG AA · ทดสอบกับขนาดตัวอักษร 200% ·
พื้นที่กดอย่างน้อย 44x44 pt · ทดสอบด้วย VoiceOver ภาษาไทย

### 12. มีภาษาไทยภาษาเดียว

แรงงานในไร่ชาเชียงรายจำนวนมากพูดภาษาพม่า ไทใหญ่ หรือลาว **คนที่ถือมือถือ
ถ่ายใบชาจริง ๆ อาจอ่านภาษาไทยไม่ออก** ถ้าเป้าหมายคือ "ใช้ได้ทุกคน" นี่คือ
ช่องว่างที่ใหญ่ที่สุดในระดับนี้

อย่างน้อยต้องมี: โครงสร้างแยกข้อความออกจากโค้ด · และผลตรวจที่สื่อด้วย
ภาพหรือสีได้โดยไม่ต้องอ่าน

### 13. ไม่มีการแนะนำการใช้งานครั้งแรก

แอปเปิดมาที่หน้าสแกนทันที ไม่มีอะไรบอกว่ามันทำอะไรได้และทำอะไรไม่ได้
**เมื่อรวมกับข้อ 1 นี่เกือบเป็นเรื่องความปลอดภัย** ผู้ใช้ต้องรู้ก่อนกดว่า
โมเดลวัดผลจากภาพโคลสอัพใบเดี่ยว และคำตอบไม่ใช่คำวินิจฉัยที่แน่นอน

หน้าจอมีข้อความเตือนเรื่องภาพโคลสอัพอยู่แล้วและเขียนถูก แต่ผู้ใช้เห็นมัน
ตอนที่กำลังจะกดถ่ายแล้ว

### 14. ไม่มีช่องทางบอกว่าคำตอบผิด

ผู้ใช้ที่เจอข้อ 1 ทำอะไรไม่ได้เลย และเราไม่ได้ข้อมูลกลับมาปรับปรุงโมเดด้วย
ปุ่ม "ผลนี้ไม่ถูกต้อง" ที่เก็บภาพกับผลไว้ (โดยขออนุญาต) คือทั้งทางออกของผู้ใช้
และเป็นแหล่งข้อมูลสนามชุดแรกที่จะแก้ข้อ 2

### 15. ต้องดาวน์โหลด 30.7 MB ก่อนใช้ออฟไลน์

บนเครือข่ายภูเขาที่ไม่เสถียร ซึ่งเป็นเหตุผลที่สินค้านี้มีอยู่ **30.7 MB
คือกำแพง** WASM 14.2 MB บวกโมเดล fp32 16.8 MB

fp16 เคยประเมินว่าจะลดเหลือราว 8.4 MB แต่ **ยังไม่ทดสอบ** และ int8
ถูกปฏิเสธไปแล้วเพราะขยับความน่าจะเป็นไป 0.248 เทียบขอบ 0.05
**ต้องวัด fp16 ด้วยเกณฑ์เดียวกัน ไม่ใช่เกณฑ์ top-1**

## ระดับ 4 — วิศวกรรมและการปล่อยของ

### 16. deploy ด้วยมือจากโน้ตบุ๊ก

`wrangler pages deploy` รันจากเครื่องคนเดียว ไม่มี CI deploy ไม่มี staging
ไม่มีทางย้อนกลับที่บันทึกไว้ ผู้ใช้จริงต้องการทั้งสามอย่าง

### 17. สองข้อที่พบตอนรีวิว PR #20 — แก้แล้วใน PR #30 รอการตรวจ

**ก. `queue.ts` ทิ้งผลที่ไม่ใช่ `full` อย่างเงียบ ๆ**
เดิมมันโยน error ดัง ๆ ตอนนี้ `filter` ทิ้ง รายการนั้นจึงไม่ถูกบันทึก
ไม่ถูกลบออกจากคิว และ**ไม่ถูกนับ attempts** ผลคือค้างในคิวตลอดกาลแบบเงียบ
การแลกความล้มเหลวที่ดังเป็นความล้มเหลวที่เงียบ มักแย่กว่า

**ข. ตัวนับ `attempts` ไม่ครอบกรณีที่พบบ่อยที่สุด**
`attempts` เพิ่มเฉพาะใน `applyBatch` ซึ่งไปถึงก็ต่อเมื่อ request สำเร็จและ
envelope ถูกต้อง **กรณีต่อเซิร์ฟเวอร์ไม่ได้เลยจึงไม่เคยนับ** เพดาน 3 ครั้ง
ไม่ทำงานกับสถานการณ์ที่เจอจริงบน static deploy

**สถานะเมื่อ 2026-10-23: แก้แล้วทั้งสองข้อใน PR #30 แต่ยังไม่มีใครตรวจ**
ข้อ ก. และ ข. อยู่ในคอมมิต `49a01b6` และ `d995d46` ของ `fix-queue-worker-issues`
**ห้ามขีดข้อนี้ทิ้งจนกว่าจะรัน probe ซ้ำ** คอมมิตที่แก้ข้อ J และ K เข้ามา
หลังรีวิวจบ จึงยังไม่ถูกวัดแม้ครั้งเดียว ดู [STATE.md](STATE.md) หัวข้อ 2026-10-23

ทั้งสองข้อไม่ใช่ตัวขวางเดโม แต่จะกัดเมื่อมีผู้ใช้จริงและเซิร์ฟเวอร์มีปัญหา

### 18. PR ที่เปิดค้าง — ข้อความเดิมหมดอายุแล้ว

เดิมข้อนี้พูดถึง PR #14 ซึ่ง **ปิดไปแล้ว** (`CLOSED` ไม่ใช่ merge) พร้อมกับ #15

**ที่เปิดค้างจริงเมื่อ 2026-10-23 มีสามใบ** #30 (คิวออฟไลน์และ error ของ ONNX
รอ probe ข้อ J และ K) · #32 (ค่า threshold ของด่านตรวจพืช SonarCloud ตกด้วย
`C Reliability Rating on New Code`) · #33 (ใบสั่งงานของ Codex)
**#32 เป็นใบที่ขวางงานคนอื่นอยู่** เพราะค่า `leaf` ถึง Codex ไม่ได้จนกว่ามันจะ merge
